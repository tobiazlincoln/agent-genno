Project Overview 
This document describes the security review of Zolana. The work was undertaken from 
September 7th, 2026 to October 13th, 2026. 
The following contract list is included in our scope: 
programs/shielded-pool/src/*​
program-libs/tree/src/*​
prover/server/circuits/gadget/*​
prover/server/circuits/ring-utils/*​
prover/server/circuits/spp_merge/*​
prover/server/circuits/spp_transaction/* 
The team performed a manual audit of all the files in scope. During the manual audit, the Certora 
team discovered bugs in the code, as listed on the following pages. 
Protocol Overview 
Zolana is a privacy protocol on Solana that supports deposits, confidential transfers, and 
withdrawals of SOL and supported SPL tokens. Balances consist of UTXOs, individual records of 
spendable value backed by assets held in the Shielded Pool Program. Zero-knowledge proofs 
validate transfers without exposing private amounts and assets, while the program checks 
authorization and prevents double spending.

Assessment Methodology 
Our assessment approach combines design level analysis with a deep review of the 
implementation to ensure that a protocol is secure, economically sound, and behaves as 
intended under realistic conditions. 
At the design level, we evaluate the architecture, the economic assumptions behind the protocol, 
and the safety properties that should hold independently of a specific chain or environment. This 
process includes reviewing internal and cross protocol interactions, state transition flows, trust 
boundaries, and any mechanism that could be exploited to extract value, deny service, or alter 
core system behavior. At this stage, a focused threat modelling exercise helps identify key attack 
surfaces and adversarial capabilities relevant to the system. Design level issues often relate to 
incentive structures, governance implications, or systemic behavior that emerges under 
adversarial conditions. 
Implementation analysis focuses on the concrete behavior of the code within the execution 
model of the target chain. This involves reviewing the correctness of logic, access control, state 
handling, arithmetic behavior, and the nuanced behaviors of the chain environment. Familiar 
classes of vulnerabilities such as faulty permission checks, precision issues, or unsafe 
assumptions often surface at this layer. These findings require context aware reasoning that 
takes into account both the code and the architectural intent. 
To support this analysis, the codebase is examined through repeated manual passes and 
supplemented by automated tools when appropriate. High-risk logic areas receive deeper 
scrutiny, invariants are validated against both design intent and actual implementation, and 
potential vulnerability leads are thoroughly investigated. Automated techniques such as static 
analysis, fuzzing, or symbolic execution may be used to complement manual review and provide 
additional insight. 
Collaboration with the development team plays an important role throughout the audit. This 
helps confirm expected behaviors, clarify design assumptions, and ensure an accurate 
understanding of the protocol’s intended operation. All findings are documented with clear 
reasoning, reproducible examples, and actionable recommendations. A follow up review is 
conducted to validate the applied fixes and verify that no regressions or secondary issues have 
been introduced.

Threat and Security 
Overview 
System model and review scope 
Zolana implements confidential asset transfers on Solana using unspent transaction outputs 
(UTXOs), or notes. The Shielded Pool Program holds SOL and token collateral, records note 
commitments, verifies zero-knowledge proofs, and records nullifiers that prevent repeated 
spending. Deposits move public assets into custody and create notes; transfers consume notes 
and create new ones; withdrawals release collateral; merges consolidate notes. Authorized 
foresters maintain the nullifier tree through proved batch updates and reclaim temporary 
account rent. 
The manual review focused on the shielded pool program (SPP), tree library, and transaction, 
merge, and nullifier-update circuits. Reviewed flows included deposits, public settlement, 
multi-tree transactions, cached spends, delegated merges, tree initialization, administrative 
controls, fee collection, batch processing, and nullifier-account cleanup. SDKs, the user registry, 
indexer, and custom ring programs supplied integration context but they’re technically out of 
scope for this review. 
Expected security invariants 
The review examined the following intended invariants: 
-​ Value conservation and collateral: Value is conserved separately for each asset, and 
newly created notes are backed by deposited collateral or consumed notes. 
-​ Authorization: Spending requires the applicable owner, ring, or delegated authorization. 
Application-bearing notes must satisfy their owner-authorization requirements. 
-​ Double-spend prevention: Real inputs prove commitment inclusion, and nullifiers are 
correctly derived and distinct. Historical roots must remain usable without allowing 
repeated spending. 
-​ Safe maintenance: Temporary nullifier accounts remain open until cleanup is safe. Queue 
transitions, batch updates, and capacity reservations preserve spendability. 
-​ Merge recovery: Merges preserve ownership, asset, and value while leaving the resulting 
note recoverable by its owner. 
​

-​ Proof and execution consistency: Amount ranges, field encodings, tree routing, and 
public-input hashes agree across Rust and Go. Failed transactions roll back state changes 
and settlement. 
Trust boundaries and security assumptions 
Depositors authorize funding, while note owners authorize ordinary spending through Solana 
signatures or in-circuit P256 verification. Custom rings authorize cross-program calls and 
impose additional policy restrictions. An enabled ring-authority path can replace owner 
signatures, subject to ring authorization and knowledge of the required note secrets. Delegated 
merging relies on registry opt-in and preserves ownership without requiring a signature for each 
merge. 
Protocol authorities control configuration, admission, and maintenance permissions; fee 
authorities control tree charges and reserve recovery. These privileges create distinct availability 
and economic risks. 
Security assumes correct Solana execution and transaction atomicity, sound cryptographic 
primitives, secure Groth16 setup, and matching circuit and proving/verifying-key artifacts. Token 
custody depends on validated SPL Token and Token-2022 accounts and supported extension 
behavior. 
Indexer data is checked through accepted roots and proofs, but indexer availability affects wallet 
operation. A hosted prover receives private witnesses and therefore introduces a confidentiality 
boundary. Applications must validate payloads against committed hashes, and ring programs 
must enforce their intended restrictions on public settlement and signer privileges. 
Privacy depends on the transaction path. Public deposits and withdrawals reveal amounts and 
assets, ordinary signing identities remain visible, and public cache selection can reveal additional 
links between outputs and spends. 
Attack vectors considered 
The threat model included malicious transaction submitters and depositors, abusive or 
compromised authorities, malicious delegated mergers, and unsafe application or ring 
integrations.

The review considered unauthorized note creation, forged application state, replay and double 
spending, malformed proofs and encodings, account substitution, cross-program signer 
escalation, stale maintenance updates, premature cleanup, and capacity exhaustion. 
Economic review covered unexpected fee increases, payer SOL exposure, reimbursement 
attribution, and reserve accounting. Delegated merges were examined for owner recovery 
failures, while ring integrations were examined for unintended withdrawal capabilities and P256 
spending limitations. 
Testing and coverage 
Existing test coverage includes successful and rejected deposits, transfers, withdrawals, merges, 
administrative changes, proof tampering, nullifier replay, queue transitions, settlement, and 
rollback. 
Recorded review validation exercised compilation of the 8-input and 36-input merge circuits, 
valid-witness checks for the 8-input shape, recovery derivation vectors, and witness 
serialization. Property-based deposit lifecycle and input-mutation tests are present, but the 
available records do not establish a dedicated audit fuzzing campaign or execution of every 
available suite. 
Documented gaps include exhaustive public-input tampering, some exact merge state and event 
assertions, and portions of full-batch maintenance coverage. No formal verification was 
performed during this audit. 
Highest severity findings and security takeaways 
The highest severity findings were: 
-​ Deposit authorization bypass: Proofless deposits could create application-bearing notes 
for another owner without that owner’s authorization. 
-​ Excess rent reserves: Reserve calculations counted funding already held by live nullifier 
accounts, preventing surplus recovery. 
-​ Unbounded tree fees: Fee changes could block spending or consume more payer SOL 
than expected. 
-​ Delegated merge griefing: A malicious merger could combine known notes with an 
unrecoverable note, making previously spendable funds inaccessible.

High Severity Issues 
H-01: Deposits can bypass data authorization 
Severity: High 
Impact: High 
Likelihood: High 
Files: ​
programs/shielded-pool/src/
instructions/deposit/process
or.rs 
Status: Fixed 
 
Description: 
The shielded pool's proofless deposit instructions create UTXOs directly from caller-supplied 
instruction data. Each UTXO includes a data_hash that commits to application data. In the 
owner-signed Transact path, ConstrainOutput requires the owner to participate whenever a real 
output carries a nonzero data_hash. This prevents callers from creating application state on 
behalf of another owner without authorization. 
However, deposit account validation requires the depositor's signature and, for ring_deposit, 
the ring_config signature, without binding the note's owner to a signer. The shared processor 
accepts utxo_data.data_hash for deposit and data_hash for ring_deposit, checks their field 
encoding, and incorporates them directly into the UTXO commitment. A depositor can therefore 
create a note for another owner with an arbitrary nonzero application-data hash without that 
owner's participation. The ring path similarly lacks an owner-authorization check despite 
requiring ring approval. 
The resulting note has a valid commitment and can pass inclusion checks, but its committed 
data was never authorized by its owner. Applications and ring policies that rely on the 
owner-authorization invariant can accept forged application state and make decisions using 
attacker-selected data. Depending on how the application interprets data_hash, this can bypass 
authorization rules or policy limits. 
Recommendations: 
​
13 


=== PAGE 14 ===
 ​ ​
​
​
​
​
                         
 
Remove application data from proofless deposits and always commit a zero data_hash in the 
shared deposit processor. Require data-bearing UTXOs to be created through proven transaction 
paths that enforce the applicable owner-authorization constraints. 
Customer Response: 
Fixed in 1305a42.  
Fix Review: 
Fix confirmed. Both proofless deposit rails now commit a zero application-data hash, so deposits 
cannot bypass application-data authorization by supplying their own hash.

Medium Severity Issues 
M-01: Excess reserves block rent recovery from active trees 
Severity: Medium 
Impact: Medium 
Likelihood: Medium 
Files: ​
programs/shielded-pool/src/
instructions/claim_tree_lam
ports.rs 
Status: Fixed 
 
Description: 
process_claim_tree_lamports lets the fee authority recover SOL above a tree's reserve. Rent is 
the minimum balance that exempts an account from storage charges. A nullifier identifies a 
spend and prevents repeated spending. A program-derived account (PDA) stores each nullifier 
until cleanup is safe. The tree funds these PDAs and receives their balances when cleanup closes 
them. 
The claim instruction reserves the tree's own rent, fee_balance owed for maintenance, and three 
complete batches of PDA funding at the current rent. This calculation requires all three batches 
of funding to remain in the tree account. It ignores funding already held by live PDAs, so it counts 
that portion of the operating capital twice. 
Cleanup cannot remove this duplication. A PDA is closable only when its queue_index is below 
close_before_index. Completing a batch advances close_before_index to that batch's start 
index, so closing its PDAs requires completing a successor batch. The successor's PDAs must 
then remain deployed. 
For example, ignore the tree's own rent and maintenance fees: 
1.​ A tree receives 30 SOL to fund three PDA batches at 10 SOL per batch. 
2.​ Creating one batch transfers 10 SOL to its PDAs and leaves 20 SOL in the tree. 
3.​ A 10% rent decrease lowers the claim instruction's required liquid reserve to 27 SOL. The 
tree holds only 20 SOL, so the instruction returns NoClaimableTreeLamports. 
4.​ Two further batches now require only 18 SOL. The remaining 2 SOL in the tree exceeds that 
funding requirement but cannot be claimed. 
​
15 


=== PAGE 16 ===
 ​ ​
​
​
​
​
                         
 
Part or all of the surplus from a rent decrease remains unavailable to the fee authority. Closing 
older PDAs cannot eliminate the excess reserve because the newest batch must remain 
deployed. The current program therefore prevents full recovery even after all eligible cleanup 
completes. 
Recommendations: 
Account for funding held by live PDAs when calculating the liquid reserve. Track PDA creation and 
closure. Use current rent requirements and cleanup timing to calculate the additional liquid 
funding needed for continued operation. Reserve only that additional funding, the tree's own rent 
minimum, and fee_balance. 
Customer Response: 
Fixed in bbdecee. 
Fix Review: 
Fix confirmed. The tree now counts open nullifier PDAs, and the claim reserve funds only the 
additional PDAs that could still be created, plus the tree account’s own rent and its maintenance 
fee balance.

M-02: Unbounded tree fees can block spending or drain the payer's SOL 
Severity: Medium 
Impact: High 
Likelihood: Low 
Files: ​
programs/shielded-pool/src/
instructions/set_tree_fees.rs 
Status: Fixed 
 
Description: 
A nullifier identifies a spend and prevents repeated spending. Spending instructions charge the 
payer fee_per_nullifier for each nullifier and collect the fees in the tree account. 
TreeAccount::init 
stores 
the 
TreeFeeSchedule from process_create_tree without an 
insertion-fee cap. process_set_tree_fees also applies uncapped fees immediately through 
TreeAccount::set_fee_schedule. Both paths accept rates up to the integer type limit. 
The supplied CLI initialization disables permissionless creation, which otherwise lets anyone 
create a tree. With this setting, only the configured tree creation authority can choose initial fees. 
Users can review initial fees before depositing, but this does not protect them against later 
increases.  
Authorities can manage fees, but these permissions must not let them seize users' funds through 
charges that users did not approve. A malicious or compromised fee authority can still raise fees 
after the payer signs and before execution. TransactIxData contains no maximum fee that the 
payer approves, so execution can collect a higher fee than expected. 
Deposits accept trees with excessive fees, but later spending can fail because of unaffordable 
charges or overflow in fee calculations. If the transaction succeeds, it can consume most or all of 
the payer's available SOL outside the shielded pool. Taking funds beyond the payer's expected 
fee exceeds the authorities' intended permissions and justifies Medium severity. Lower fees can 
restore spending, and failed transactions reverse any forester fee transfer. A forester maintains 
the nullifier tree and receives collected fees through maintenance payments. An attacker needs 
control of, or cooperation from, the forester authority to recover these fees. 
Recommendations:

M-03: Malicious merger can lock the owner's funds 
Severity: Medium 
Impact: High 
Likelihood: Low 
Files: ​
prover/server/circuits/spp_
merge/shared/transaction.go 
Status: Fixed 
 
Description: 
Owners can enable delegated merging and provide a merger with their UTXO openings and 
nullifier_secret to generate merge proofs. Once merging is enabled, merge_transact accepts 
merges without the owner's signature. The merge circuit preserves the common owner and 
asset, sums the input amounts, and derives the output blinding deterministically. 
However, the circuit exposes no verifiably encrypted merged amount. Instead, wallet 
reconstruction requires every real input to be known and sums their amounts locally. This 
assumes that the owner knows all merged inputs, which the protocol does not enforce. A sender 
can create a valid UTXO for another owner through transact without publishing ciphertext that 
correctly reveals its amount. 
A malicious delegated merger can trigger the issue as follows: 
1.​ Create a UTXO for the owner through transact, using the same asset as the owner's 
known UTXOs, and withhold the correct ciphertext needed to recover its amount. 
2.​ Merge this unknown UTXO together with the owner's known UTXOs. The merger knows all 
input openings and has the delegated nullifier_secret, so the merge satisfies the 
ownership and value constraints. 
3.​ The owner's known inputs are consumed, but the owner cannot reconstruct the merged 
amount because one input amount remains unknown. 
The owner cannot generate a valid spending proof for the merged UTXO without its exact 
amount. Consequently, a malicious merger can make previously spendable funds inaccessible 
until the missing amount is disclosed or otherwise recovered. The output still belongs to the 
owner, but deterministic blinding alone does not guarantee that the owner can spend it. 
Recommendations: 
​
19 


=== PAGE 20 ===
 ​ ​
​
​
​
​
                         
 
1.​ Restore verifiable encryption of the merged output to the owner's registered viewing key, 
as removed in PR #171. Bind the correct ciphertext and registered key to the merge proof 
and publish the ciphertext so recovery does not depend on knowing every input. 
 
2.​ Alternatively, constrain an encrypted amount in the merge circuit: 
enc_amount = merged_amount + Poseidon(ENC_AMOUNT_DOMAIN, nullifier_secret, 
Nullifiers[0]) 
Use arithmetic in the circuit's field, a distinct encryption domain, and include enc_amount 
in the verified public-input hash and published instruction data. The owner can subtract 
the same mask to recover merged_amount. The first input is constrained to be real, so its 
single-use nullifier prevents mask reuse across successful merges. Update wallet recovery 
and the proving and verifying keys accordingly. 
 
Customer Response: 
Fixed in bbdecee. 
Fix Review: 
Fix confirmed. Now merges on the default ring binds encrypted output amount and mint 
information to the proof, allowing owners to recover notes without every input opening. For 
merges in custom rings, the ciphertext remains unverified; this has been acknowledged by Helius.

Low Severity Issues 
L-01: Tree parameters can change during initialization 
Severity: Low 
Impact: Low 
Likelihood: Low 
Files: ​
programs/shielded-pool/src/
instructions/create_tree/pro
cessor.rs 
Status: Fixed 
 
Description: 
process_create_tree creates a tree account through four allocation steps. The first step 
collects funds based on its nullifier parameters, which control how the tree records spent values. 
It does not store those parameters, the fees, or the initiator. The final step uses the values 
supplied to TreeAccount::init. 
If creation spans separate transactions, another permitted caller can complete the tree with 
different parameters or fees. With tree_creation_is_permissionless enabled, any signer can 
complete it. Otherwise, the caller must use the configured tree_creation_authority. The 
standard SDK builds identical steps, and the normal creation flow sends them in one transaction 
to prevent this interference. 
If the final batch size requires less funding, fund_tree leaves the excess in the tree without 
refunding the original payer. Only the fee authority can recover it through claim_tree_lamports 
after initialization. Existing instructions cannot change the final nullifier parameters, although the 
fee authority can update fees through set_tree_fees. 
Recommendations: 
Store the intended nullifier parameters and fees during the first allocation step. Require every 
later step to match these values before it changes the tree or transfers funds. If the initiator must 
control completion, also store a designated initialization authority. Require that authority to sign 
subsequent steps.

L-02: Batch update reimbursements are misattributed across forester workers 
Severity: Low 
Impact: Medium 
Likelihood: Low 
Files: ​
programs/shielded-pool/src/
instructions/batch_update_
nullifier_tree.rs 
Status: Acknowledged 
 
Description: 
process_batch_update_nullifier_tree accepts authorized forester proofs, caches updates 
that arrive out of order, and applies consecutive updates when their predecessors become 
available. A submission that only caches an update receives no reimbursement. However, 
CachedTreeUpdate stores only the old root, new root, and occupancy flag, so it does not retain 
the submitter's reimbursement recipient. 
When a later submission triggers application, event.num_update counts every update in the 
cascade, including proofs previously submitted by other workers. The processor calculates 
reimbursement 
for 
this 
total 
and 
pays 
it 
entirely 
to 
the 
current 
instruction's 
reimbursement_recipient. 
ProtocolConfig currently stores a single forester_authority account, but this account is 
intended to be a 1-of-N Squads smart account. Different members can submit through the same 
authority while using separate fee payers and reimbursement recipients. Independently funded 
workers can therefore incur transaction fees while the member whose submission triggers 
application receives the reimbursement attributable to their cached updates. 
Recommendations: 
Record the reimbursement recipient for each accepted cached update and credit that recipient 
when the update is applied, through supplied writable accounts or a recipient-bound claim 
balance. Alternatively, acknowledge this issue and document it so that foresters are aware of it.

L-03: Outputs can enter trees with exhausted nullifier capacity 
Severity: Low 
Impact: High 
Likelihood: Low 
Files: ​
program-libs/tree/src/lib.rs 
Status: Fixed 
 
Description: 
Each tree account contains a UTXO tree for output commitments and a nullifier tree that records 
spends. Deposit, transact, and merge append outputs based on UTXO capacity without verifying 
that the destination retains nullifier capacity to spend those outputs. 
The allow_dummy_inputs check compares remaining nullifier slots against unused UTXO leaves 
before queuing current inputs. This omits existing unspent notes from the reserve and does not 
account for the current batch's reservations. Dummy/address inputs consume nullifier slots 
without spending existing notes, while cross-tree transactions insert nullifiers into input trees 
separately from destination outputs. The nullifier tree can therefore become full while the UTXO 
tree still has room. 
Users can then deposit or receive funds that become permanently unspendable because every 
later spend fails with TreeIsFull. Existing unspent notes in that tree are also frozen. A replacement 
tree cannot recover them, since moving notes requires inserting nullifiers into the exhausted 
source tree. The impact is limited to the affected tree and requires approximately 2^40 lifetime 
nullifier reservations, making deliberate exhaustion extremely costly. 
Recommendations: 
Reserve nullifier slots for the UTXO tree's total capacity, rather than only its unused leaves. 
Replace 
allow_dummy_inputs 
with 
dummy_input_headroom, 
computed 
as 
remaining_queue_capacity minus total UTXO capacity, clamped at zero. Before inserting 
nullifiers, transact and merge should permit dummy/address inputs only when this headroom 
covers the full current input count for that tree. 
Customer Response: 
Fixed in ebca3ad.

Impact: Low 
Likelihood: Low

Description: 
The UTXO cache stores verified output commitments in a public account, allowing later 
transactions to spend them without waiting for Merkle inclusion data. A transaction's public 
read_bitmap selects cache slots, and their commitments are bound into the proof's public input 
hash. Selected entries can remain unused, so selecting a slot alone does not prove that its 
commitment was spent. 
For a successful transaction with one input, one selected cache slot, no UTXO root, and a strictly 
positive net public withdrawal, the relationship becomes conclusive: 
1.​ Balance conservation requires a real shielded input to fund the withdrawal, since dummy 
and address inputs carry no value. 
2.​ Omitting the UTXO root supplies a zero root. The input constraints require a nonzero root 
for an uncached UTXO, forcing this input to use the cache. 
3.​ The cache constraints require the input commitment to equal the selected commitment, 
and nullifier derivation binds that input to the transaction's sole nullifier. 
An observer can therefore identify when the earlier shielded output was spent, weakening its 
unlinkability. This does not break commitment hiding or recover the owner secret, shielded 
amount, asset, or recipient from the commitment. Public withdrawal details are already visible 
independently. The inference depends on the conditions above. 
Recommendations: 
Document this privacy risk in the cache and SDK guide, including the conditions that make the 
link conclusive and the fact that selecting a slot alone is insufficient.

I-01: UTXO data is not validated against data_hash 
Files: 
prover/server/circuits/spp_transaction/shared/outputs.go 
Description: 
The Shielded Pool verifies UTXO commitments that include data_hash. However, its UTXO circuit 
fields contain only the supplied hash, without the application-data bytes needed to verify it. The 
specification explicitly states that data_hash is committed unchecked and interpreted by 
application circuits and SDKs. 
On owner-signed transaction paths, ConstrainOutput requires the output owner's signature 
only when data_hash is nonzero. Consequently, nonempty application data paired with a zero 
hash does not activate this requirement, and the recipient can receive that data without signing 
the transaction. The SDK's with_utxo_data method also accepts application bytes and a 
caller-supplied hash without validating their relationship.

application payload can trust false metadata, select UTXOs that fail application checks, or 
encounter scanning and spending failures. These consequences depend on applications trusting 
the payload without checking its hash, which makes this an informational integration concern. 
Recommendations: 
If the Shielded Pool should guarantee this relationship, extend its proof constraints to recompute 
data_hash from the application data using a defined encoding and hash scheme, reserving zero 
for absent data.  
Otherwise, make the existing trust boundary explicit in SDK APIs and integration documentation: 
applications must verify the payload against data_hash before trusting it, and reject nonempty 
application data paired with a zero hash before treating it as owner-authorized state.

I-04: Sha256BE returns incorrect zero nodes 
Files: 
program-libs/hasher/src/sha256.rs 
Description: 
Sha256BE computes SHA-256 and clears the first byte of each result. Its zero_bytes method 
should return predefined hashes of empty Merkle subtrees computed with the same hashing 
rule. However, it returns the zero-node table for ordinary Sha256. The mismatch appears at level 1:

with 32 zero bytes at level 0, then compute each next level as Sha256BE::hashv([previous,

changing a lower-level value changes the input to every higher-level hash.

I-07: HashChain4 does not bind input length 
Files: 
prover/server/circuits/gadget/hashchain.go 
Description: 
HashChain4 commits to public-input transcripts and nullifier-batch values by starting with the 
first element and absorbing the remaining elements in groups of three. Each step hashes the 
current chain value and the group using four-input Poseidon. An incomplete final group is 
padded with zeros, but the original list length is never included in the commitment. 
Consequently, different-length lists have the same digest when explicit trailing zeros replace 
padding. For example: 
-​ HashChain4([a, b]) hashes Poseidon(a, b, 0, 0), with both zeros supplied as 
padding. 
-​ HashChain4([a, b, 0]) and HashChain4([a, b, 0, 0]) hash the same four values. 
Their explicit zeros are indistinguishable from padding. This equality applies while the 
added zeros fit within the final group; crossing the group boundary introduces another 
hash operation. 
The reviewed transaction and merge paths use fixed transcript layouts and select the 
corresponding verifying keys, while nullifier-batch circuits enforce their configured batch length. 
SPP also rejects zero nullifiers and output hashes in published transaction slots. No current 
proof-bypass or state-integrity impact was identified. A future caller accepting meaningful 
trailing zeros in variable-length lists could nevertheless mistake distinct lists for the same 
commitment. 
Recommendations: 
Keep HashChain4 restricted to callers that enforce a fixed input length or otherwise exclude this 
padding ambiguity. If variable-length commitments are required, include an explicit length and 
domain tag in the hashed preimage.
